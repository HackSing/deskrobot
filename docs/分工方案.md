# 三人分工方案

更新日期：2026-09-19。以仓库当前 main 的代码为准。每个人先读 README、AGENTS.md 和 contracts.py，再读自己那一节。

## 1. 现状盘点

已经能跑的：状态机 `core/orchestrator.py`、契约 `contracts.py`、看板接口 `web/server.py`、三套假模块 `mocks/`、本地存储 `brain/store.py`、资料提取 `brain/materials.py`、两组测试 `tests/`。`python run_local.py` 用假语音、假机器人、假大脑可以走完一整场会议。

| 模块 | 现状 | 剩余工作量 |
| --- | --- | --- |
| 语音 `speech/` | `providers.py` 里 ASR 和 TTS 两个函数直接抛 NotImplementedError，真链路整体不通 | 最重，唯一从零开始的模块 |
| 机器人 `robot_io/` | 代码写完，从未上过真机，`real.py` 留有两处 TODO | 中，全靠真机核对 |
| 大脑 `brain/` | 真实现写完，从未接过真 LLM，留有两处 TODO | 中，不需要机器人 |
| 页面 `web/` | 一个 104 行的最小桌面页，三个 tab 已有但素面；没有 H5、没有扫码、没有角色 | 重，H5 扫码加入是全新功能 |

## 2. 分工原则

- README 原来按四个人分成 A、B、C、D。三个人时把 C 大脑和 D 页面合给一个人，因为这两块都不占机器人。A 和 B 各自保留，因为两者都要抢机器人，且语音是最长的关键路径。
- 目录边界不重叠，AGENTS.md 的规则不变：只改自己的目录，模块之间只通过 contracts.py 交互，SDK 调用包在 `asyncio.to_thread` 里，key 只放 .env。
- 假设只有一台机器人，机器人时间按第 7 节排班。
- 假模块一个都不删，任何真模块出问题用 `USE_FAKE_*` 开关一键退回。

## 3. 目录归属

| 人 | 角色 | 独占目录和文件 | 需要的资源 |
| --- | --- | --- | --- |
| P1 | 集成 + 机器人 | `core/` `robot_io/` `main.py` `app.py` `app.json` `contracts.py` `requirements.txt` `tests/test_flow.py` | 机器人 |
| P2 | 语音 | `speech/` `tests/test_commands.py` | 机器人麦克风和扬声器，云端 ASR/TTS 的 API |

## 4. P1 集成 + 机器人

### 高优先级，必须完成

1. **真机核对反馈表 `robot_io/cues.py`**
   - 12 个 cue 共用了 10 个行为 ID：standby、listening、awake_idle、thinking、speaking、speechless、agent_question、shock、happy、sad。设备没有的 ID 会被 `_try` 静默吞掉，不崩但没反应，所以必须逐个触发看。
   - 同时核对侧灯和底灯的 zone 名 side / bottom，灯效名 blink / status_pulse / breathing，以及 `progress_color` 的绿、黄、红三段。
   - 做法：起 `run_local`，在看板底部调试框依次输入指令，或写一个临时脚本按表遍历 `robot.cue()`。临时脚本不提交。
   - 产出：改好的 `cues.py`，表里每一行都在真机上验证过。
2. **守门人**
   - 合并：每次 `git pull --rebase` 后跑 `python -m pytest -q` 和 `run_local`，红了先修再推。
   - 依赖：任何人要加包，由 P1 同时写进 `app.json` 和 `requirements.txt`。
   - 契约：`contracts.py`、`main.py`、`app.py` 只有 P1 改，改完在群里通知。
   - 环境变量：新增的变量由 P1 同步写进 `.env.example`。
   - 联调：两次联调由 P1 主持，问题按"谁的目录谁修"，跨目录的由 P1 裁决。
3. **状态机调参 `core/orchestrator.py`**
   - `OFF_TOPIC_EVERY` 跑题检查间隔、`CONFIRM_WAIT` 每条待办等拍背的秒数、超时播报的措辞和时机。
   - 跑题的两级反馈：第一次只做表情，第二次才开口，看现场体感是否合适。
   - 播报期间 `_busy` 锁会让后面的指令排队，注意演示时连续说话会不会显得迟钝。
4. **验收标准**
   - 给三个模块各定一份验收清单，联调时逐条打勾。第 4、5、6 节末尾的"验收"是初稿，P1 定稿。

### 次优先级

- 拍背输入：确认 press 和 long_press 事件能到达回调，解决 `real.py` 里的 TODO，即 `inputs.wait` 超时到底抛哪种异常。
- 跟随与点头的冲突：人脸跟随开启后云台归跟随服务管，记重点时的点头可能被覆盖。要么点头前暂停跟随，要么去掉俯仰动作只留灯效。
- 给 P3 提供公开的开始会议方法：目前 H5 上的"开始会议"按钮走 `/api/debug/say` 发一句开会指令就能用，有空再在 Orchestrator 上加一个公开的 `start(project)`。

### 验收

- 真机上 12 个 cue 各触发一次都有可见反应，底灯三段颜色正确。
- 拍背能确认待办，长按能结束会议。
- 两次联调按时开始，冻结后没有功能改动。

## 5. P2 语音

以下全部必做，按顺序推进。团队已有云端 ASR 和 TTS 的 API，直接接。

1. **先让机器人开口：`providers.tts`**
   - 接云端 TTS。输出必须是 16 位单声道 PCM，采样率 24000，单次不超过 4 MiB，长文本要分段。
   - 云端返回 mp3 或其他格式时需要解码，解码用的包走 P1 加依赖。
   - 失败时记日志、直接返回，不要把异常抛到状态机，否则整场会议卡住。
   - 可以先在电脑上用本地播放器听输出，再上真机用 `robot.audio.play_pcm` 试。
2. **再让机器人听懂：`providers.asr`**
   - 接云端 ASR。输入是 16 kHz 单声道 16 位 PCM 的整句，识别不出返回空字符串，单次超时不超过 5 秒。
   - 热词要传机器人名字和参会人姓名，否则"主持人"和人名容易被识别成别的词。热词列表由 `RealSpeech.hotwords` 传入，P3 的 H5 加入流程会把扫码进来的名字写进会前准备，P2 在开场时读一次。
   - 没有机器人时用本地 wav 文件喂 `asr()` 测。
3. **切句阈值 `speech/segmenter.py`**
   - 目前音量阈值 500、静音 700 毫秒、最短 400 毫秒、最长 15 秒，都是默认值。在真实会议室用真麦克风录三段试：安静、一个人正常说话、两个人交替说话。
   - 建议把三个参数改成读环境变量，现场能改不用动代码。
4. **回声**
   - 播报期间 `_speaking` 会丢帧，播报结束只留 0.3 秒尾巴。真机上要试机器人会不会听到自己说的话并触发指令。不够就延长尾巴，或播报结束后重置 segmenter 的缓冲。
5. **指令说法与单测 `speech/commands.py`**
   - 补口语变体：开会吧、开始吧、记一下、标一下、散会、先到这里。每加一种说法补一条 `tests/test_commands.py`。
   - 注意规则顺序有意义，兜底是 ask，别让新规则把提问吃掉。

没有机器人时的开发方式：只有 `speech/real.py` 里读麦克风和放音频那两处需要真机，其余全部可以离线做。

### 验收

- 对着机器人说"主持人，开始供应商报价的会议"，被识别并得到播报回应。
- 一轮问答往返不超过 5 秒。
- 连续说 10 句，至少 8 句转写可用。
- 机器人播报期间不会自己触发任何指令。

## 6. P3 大脑 + H5 页面

除演示外全部必做。演示彩排由全员承担，P1 牵头。

### 6.1 大脑 `brain/`

1. **接真大脑**：在 `.env` 里配 `LLM_URL`、`LLM_KEY`、`LLM_MODEL`，把 `tests/test_flow.py` 的四步用真大脑手动走一遍。
2. **JSON 解析加保护**：`real.py` 的 `_json` 用正则抓第一个大括号到最后一个大括号，模型多说几句就解析失败，异常会让那条指令无声丢失。在提示词里加硬约束，解析失败重试一次，仍失败返回"这个我没找到"。
3. **联网搜索**：`LLM_SEARCH_EXTRA` 按供应方文档配，专门测台词里"查一下芯片停不停产"那一步。
4. **长转写压缩和资料超限摘要**：`real.py` 与 `materials.py` 里的两处 TODO，排在 H5 之后做。

### 6.2 H5 页面与扫码加入

这是新功能，以下是可直接开工的设计。手机端 H5 为主，桌面大屏沿用现有布局做响应式即可。

**角色**

| 角色 | 谁 | 能做什么 |
| --- | --- | --- |
| 发起人 | 会议组织者，一场只有一个 | 填会议信息、上传背景资料、发起会议、出示二维码、点开始会议、作废房间 |
| 参与人 | 扫码进来的人，可多个 | 选自己的名字加入、看会中看板、散会后收到纪要 |
| 大屏 | 会议室电脑或电视 | 只看，用现有桌面页 |

**顺序，必须严格按这个走**

1. 发起人打开 H5 发起页，填项目、议程、参会人、背景，点"发起会议"。服务端保存会前准备，创建一个房间，状态为 open，返回发起人令牌和加入链接。
2. 发起页切换成发起人视图：显示加入链接的二维码、已加入的人、上传资料区、"开始会议"按钮。
3. 发起人上传背景资料，可以多份，上传时校验发起人令牌。
4. 参与人扫码打开加入页。加入页先查房间状态：没有房间或房间已结束，显示"会议还没发起，请等发起人发起后再扫码"，不能进；房间是 open 或 in_meeting，显示名字选择，选完加入。
5. 加入的名字追加进会前准备的参会人列表并保存，这样大脑生成待办时负责人能对上名字，P2 的热词也能拿到。
6. 发起人点"开始会议"，或有人对机器人说开会指令，状态机进入 meeting，房间状态跟着变成 in_meeting。会中所有 H5 页面通过 WebSocket 收快照，显示会中看板。
7. 会议结束、待办逐条拍背确认、纪要保存后，房间状态变成 ended，服务端把纪要推到所有连着的 H5 页面，每个页面自动切到纪要视图，自己名下的待办高亮。
8. 房间 ended 后二维码失效，下一场由发起人重新发起。

**门禁规则**

- 加入链接里带房间令牌，令牌不对或房间不是 open / in_meeting 一律拒绝。
- 一次只允许一个未结束的房间。已有未结束房间时再发起，返回冲突，发起人可以先作废。
- 发起人操作校验发起人令牌，参与人不能上传资料、不能开始会议。

**页面清单**，建议单独一个 `web/static/h5.html` 用 hash 路由，保留 `index.html` 给大屏

| 页面 | 路由 | 内容 |
| --- | --- | --- |
| 发起页 | `#host` | 表单、发起按钮；发起后变成二维码、已加入名单、上传资料、开始会议、作废 |
| 加入页 | `#join?t=令牌` | 房间状态提示，名字选择，加入按钮 |
| 会中看板 | `#live` | 计时、当前议题、进度条、实时转写、已记重点、最近问答，手机竖屏可读 |
| 纪要页 | `#minutes` | 结论、待办、未决问题、重点；自己的待办高亮，拍背确认状态可见；每条待办可点"完成" |

**新增接口**，都在 `web/server.py`

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/api/session` | 发起会议。body 与原 `/api/prep` 相同。保存会前准备，创建房间，返回 session_id、host_token、join_url。已有未结束房间返回 409 |
| GET | `/api/session` | 当前房间：status、project、已加入名单、是否允许加入。没有房间返回 status 为 none |
| POST | `/api/session/join` | body 带 token 和 name。校验后登记参与人，返回 client_id |
| POST | `/api/session/materials` | 发起人上传资料，带 host_token。内部复用 `extract_text` 和 `store.save_prep` |
| POST | `/api/session/start` | 发起人点开始。先用 `orch.on_utterance` 发一句"主持人，开始某某的会议"，P1 提供公开方法后再换 |
| POST | `/api/session/close` | 发起人作废房间，演示重来时用 |

现有接口不变。`/ws` 推送前由 `server.py` 把 session 字段合并进快照，不改状态机。`/api/minutes/latest` 给刷新后的手机页拉纪要。

**房间数据**，先放 `server.py` 的内存字典，演示够用；有空再落到 `data/session.json`

- session_id、project、host_token、join_token、status、created_at
- participants：每人 name、client_id、joined_at
- meeting_id：状态机开场后回填

**状态联动**：`server.py` 在 `build_app` 里用 `orch.bus.subscribe` 订阅快照。快照 state 变成 meeting 时房间置 in_meeting；state 回到 idle 且 minutes 非空且房间是 in_meeting 时置 ended，并把带纪要的快照广播出去。

**纪要推送**：连着的页面收到 status 为 ended 的快照就切纪要视图；关掉又打开的页面先查 `/api/session`，再拉 `/api/minutes/latest`。参与人的 client_id 和名字存在浏览器 localStorage，用来高亮自己的待办。

**二维码**：把一个 JS 二维码库放进 `web/static/vendor/`，前端生成，不加 Python 依赖，不依赖外网。加入链接用 `lan_ip()` 和 `WEB_PORT` 现算，换网络后重新发起即可。

**需要 P1 配合的点**

- 确认 `web/` 整体归 P3。
- 开始会议的公开方法，非必需，先用发指令的办法。
- 快照里若要加字段，先说。目前设计不需要。

## 9. 协作规则

在 AGENTS.md 基础上补几条。

- 只用 main，推送前 `git pull --rebase`。三人目录不重叠，冲突概率很低。
- 共享文件只有 P1 改：契约、入口、依赖清单、`.env.example`。
- 每人自己的 `.env` 不提交。
- 假模块一个都不删，`USE_FAKE_*` 是演示当天的保命线。
- 联调发现的问题谁的目录谁修，跨目录的记给 P1 裁决。
- 临时脚本、录音、截图不进仓库。

## 10. 风险与保底

- **语音整个不通**是最大风险。保底：看板底部的调试输入框和拍背按钮不靠麦克风也能走完整场，台词照常演。
- **云端 TTS 不通**时用免 key 的 edge-tts 做备胎，SDK 例子里有现成的。
- **行为 ID 与文档不符**不会崩，只是机器人没反应，所以 P1 第一小时必须核对完。
- **LLM 输出不是 JSON**时用假大脑兜底，假大脑对台词四步的覆盖是够的。
- **手机和电脑不在同一局域网**会导致二维码打不开。现场先确认所有设备连同一个 Wi-Fi，不行就开热点。
- **H5 做不完**时的最小可交付：发起页出二维码、加入页能进、会中看板能看，纪要推送退化为散会后手动刷新纪要页。
- **负载调节**：P3 现在最重，P1 反馈表核对完后优先帮 P3 做 `server.py` 的接口，P3 专注页面。
